THE WAVE_CYCLES / PI-SIDE HASH PROBLEM
========================================
UPDATE (2026-09-15): the website-side model described below has changed
since this file was first written — see "WHAT CHANGED" first if you read
the original version already.

WHAT CHANGED
------------
The website no longer treats WAVE_CYCLES 1-5 as an equally-acceptable
range. Each lab now ships with exactly ONE starting (default) value and
exactly ONE correct target value — everything else is treated the same
as any other unauthorized edit:

  - wave.py:      WAVE_CYCLES starts at 1. Only WAVE_CYCLES = 5 is the
                  lab's objective / queueable. 2, 3, and 4 are rejected
                  exactly like any other tampered line, not accepted as
                  "still valid."
  - fist_bump.py: ENABLE_HEAD_NOD starts at False. Only
                  ENABLE_HEAD_NOD = True is queueable.

This lives in api/_lib/canonical-source.js's TUNABLES map and is covered
by test/canonical-source.test.mjs.

CONTEXT
-------
The Wave lesson's Code Editor lets a student change WAVE_CYCLES in wave.py
and submit it to the real robot via "Queue on Robot". The website
(api/_lib/canonical-source.js) accepts only the one target value above —
every other line of the file still has to match the verified version
exactly.

That website-side check is confirmed working: the validate/submit
endpoint (api/robot/queue.js, action "validate"/"submit") correctly
accepts only the target value and rejects everything else, and this is
covered by automated tests.

WHY THE ROBOT MAY NOT MOVE ANYWAY
----------------------------------
Submitting and getting a job approved is NOT the same as the robot
running it. The actual path is:

  1. Student submits code -> api/robot/queue.js validates it, stores
     `code` and `code_sha256` in the robot_jobs table.
  2. An admin approves the job.
  3. The bridge (bridge/server.js) polls api/robot/agent.js
     ("dispatch-queue"), which atomically claims the job and hands the
     bridge { code, sha256 } for that job.
  4. The bridge relays that straight to the Pi over the WebSocket as a
     job.run message. bridge/server.js does not check the hash itself —
     it is a pure relay (see the `sha256: job.sha256` line it sends).
  5. The physical Pi-side agent receives job.run and is the thing that
     actually moves the robot.

Step 5's code is NOT in this repository (it lives in sway-r/swayform_ws).
Originally, everything observed pointed to the Pi agent doing its own
hash check independent of the website — comparing the incoming `sha256`
against one hardcoded known-good hash for wave.py (the original
WAVE_CYCLES = 3 version) and silently refusing to execute anything whose
hash didn't match, with no error surfacing back through the website.

WHAT THE PI AGENT SHOULD ACTUALLY DO (confirmed with the project owner)
-------------------------------------------------------------------------
The Pi should not be re-deciding whether submitted code is "allowed" at
all. That decision already happened upstream, twice: canonical-source.js's
byte-exact + single-target check, and a human admin's explicit approval.
By the time a job reaches the Pi, it has already passed both gates.

So, concretely:

  - The `sha256` field in job.run is a TRANSPORT-INTEGRITY check only —
    "did these bytes arrive intact from website -> bridge -> Pi" — not an
    authorization check. The Pi should compute sha256(received code) and
    compare it to the `sha256` it was sent IN THAT SAME MESSAGE, not
    against some separately hardcoded "known good" value. If they don't
    match, that's corruption/tampering in transit, not a content decision.
  - Do NOT maintain a second, hand-kept allowlist of "acceptable" full
    source hashes on the Pi. That is the actual bug: it silently
    re-rejects content the website already approved, with no error
    surfaced anywhere, and it will go stale every time anyone edits
    wave.py/fist_bump.py's source (as already happened repeatedly).
  - The ONLY thing the Pi should independently validate is physical:
    every commanded joint position must fall within the max/min limits
    already defined in config/robot.yaml (sway-r/swayform_ws). This is a
    hardware safety clamp, not a content-approval decision, and it should
    stay cheap/fast since it runs on every job. If a job fails this
    check, the Pi should report that back (job.exit / an error) so it's
    visible on the website/Terminal, not just silently do nothing.

If you need the fastest possible unblock right now before doing the full
fix above, these are today's exact target/default sha256 hashes (full
file, UTF-8, as currently shipped in portal/data/workspace-files.js —
computed the same way api/robot/queue.js hashes submitted code):

  wave.py,      WAVE_CYCLES = 1 (default):      fe028f7d9ebb6018935563e8db035a606602b85da2dda41c12e4b0719629ea5a
  wave.py,      WAVE_CYCLES = 5 (target):        3452f06735d15c59f92258058b016cb12392c06a3b94bfbfd4404fde3fbdb8a3
  fist_bump.py, ENABLE_HEAD_NOD = False (default): a81911924d2ca26f938724dd7a813a36203e299303d7d5b1ea110f543b582831
  fist_bump.py, ENABLE_HEAD_NOD = True (target):   dd338ded927dfe58aa3f711825671804b4bf3ed9d40354860d10f83cd5315ec3

These are a stop-gap, not the recommendation. Only the two "target" hashes
above should ever actually need to run on the real robot (Queue on Robot
only ever submits a job once it exactly matches the target) — but they
will go stale again the instant anyone edits either file's source, which
is exactly why the fix above (stop hash-pinning content, check joint
limits instead) is the one actually worth doing.

BOTTOM LINE
-----------
The website is doing what was asked: one default, one correct target,
admin approval required, everything else rejected. Nothing will actually
run on the physical robot until the Pi agent stops re-deciding content
approval on its own and instead trusts the website+admin gate, using its
own local check only for joint-limit safety. Until that happens, a
student who does everything right may see "Queued" and "Approved" and
then nothing happen physically — worth deciding whether to warn students
about that in the meantime.
