Common Questions

What program directors ask before they apply.

Is SwayForm available to individual students or the general public?
No. SwayForm is available exclusively to accredited educational institutions. Each application is evaluated individually. There is no consumer channel and no plans to create one.
What technical background do instructors need?
Comfort with the Linux command line is sufficient. Prior ROS 2, robotics, or embedded systems experience is not required. The instructor track within the Learning Hub covers every concept students will encounter, in the same sequence students encounter them.
Does the platform require internet access?
No. The robot, Learning Hub, and all associated software operate entirely on the local network. There are no cloud services, no external dependencies, and no ongoing subscriptions. Programs with restricted internet access can run the full curriculum without modification.
How many units does a program need?
One unit supports a robotics club of up to 15 students in rotation. For a classroom course, one unit per group of four is the standard configuration. Programs deploying across multiple sections should contact us directly for volume guidance.
What is included with each unit?
The robot, fully assembled and validated. All software pre-installed. Lifetime access to the Learning Hub. Instructor onboarding package with lab rubrics, pacing guide, and full curriculum map. A dedicated support contact for the duration of the program year.
What does the application process involve?
Submit the program profile form on this page. We review each application for institutional context, infrastructure readiness, and program fit. Accepted programs are contacted within five business days and introduced to their SwayForm support contact before deployment.
Can the curriculum be integrated into an existing course?
Yes. The four-quarter structure is modular by design. Programs can begin at any quarter, run a condensed single-semester track, or integrate individual labs into an existing engineering or computer science curriculum. All lab materials are available for instructor adaptation.
What happens if a hardware component fails?
Every mechanical and electronic component is an off-the-shelf part with a documented replacement procedure. SwayForm provides a hardware repair guide, replacement parts at cost, and direct engineering support for any issue that arises during the program year. No component is proprietary.

Not every student needs full SSH access. SwayForm's tiered model lets instructors grant exactly the right permissions for each group's skill level and responsibility.

Safety

The robot does not trust student code.

Every joint command passes through the hardware driver before anything moves. The driver validates joint names, clamps angles to safe ranges, and converts values — regardless of what the student published.

Green Zone — Student Safe
  • ✓ Publish to /swayform/joint_targets
  • ✓ Subscribe to any read topic
  • ✓ Run demos and lab packages
  • ✓ Use rqt_image_view
  • ✓ Modify code in swayform_labs
Yellow Zone — Supervised
  • ⚠ Publish to /swayform/neutral
  • ⚠ Modify joint range config
  • ⚠ Run two nodes publishing simultaneously
  • ⚠ Disable driver clamp for testing
  • ⚠ Run at max speed sequences
Red Zone — Instructor Only
  • ✗ Modify driver source code
  • ✗ Change I²C channel assignments
  • ✗ Power rail modifications
  • ✗ Flash servo firmware
  • ✗ Access Pi GPIO beyond approved pins
What happens when a student sends an out-of-range command?

The driver receives the message, checks each joint's requested angle against its configured safe range (e.g., neck_yaw: ±45°), clamps the value to the boundary, logs a warning with the clamped value, and executes the clamped angle. The robot never ignores the command — it does the safest version of what was asked. The student sees the warning in the driver log and can diagnose the issue.

Power architecture

The servo rail and Pi rail are intentionally separate. Current spikes from motors should never reset the Pi.

Wiring block diagram

Common electrical issues

Servo twitching randomly
Voltage sag under load. Buck converter undersized or servo rail underpowered. Check voltage at PCA9685 V+ pin under load (should stay above 5.8V).
Pi reboots when robot moves
Servo rail and Pi rail sharing ground but not properly isolated. Inrush current from multiple servos starting simultaneously spikes the Pi supply. Use separate buck converters.
One side of robot dead
Second PCA9685 not initializing. Check I²C address (0x41 vs 0x40 jumper). Run i2cdetect -y 1 on Pi and confirm both addresses appear.
Grinding noise from joint
Servo hitting mechanical stop. Out-of-range command bypassing clamp, or wrong joint name published. Cut servo power immediately. Verify angle limits and joint name mapping.

Before You Touch the Robot

The robot does not know your intent. A command that looks correct in code can still damage a joint if the angle is out of range. Read this before your first session.
⏱ 5 min
🔒 Required: Read before Lab 01

Physical safety rules

  • Keep at least 30cm of clearance around the robot when any code is running.
  • Never force a joint manually while the robot is powered. Servos resist manual movement when powered — forcing them strips gears.
  • Power sequence: turn on the Raspberry Pi first, wait for it to boot, then enable the servo power rail. Never the other way around.
  • If a servo makes a grinding or clicking noise, cut servo power immediately using the power switch. Do not re-run the same command. Report it to your instructor.
  • Do not run code that hasn't been checked by your instructor until you're on Tier 3 access (edit + run).
Robot Reality

When a servo hits its mechanical stop and keeps receiving a stall command, it draws maximum current — around 1.4A for the MG996R — and converts that into heat. A few seconds of stall is uncomfortable. A few minutes will damage the gearbox. The software driver clamps values, but your code should clamp them first as a habit.

Emergency stop procedure

  1. Press Ctrl+C in the terminal running your node. This kills the node immediately.
  2. If the robot is still moving (inertia, another node), locate the servo power switch on the electronics bay and toggle it off.
  3. If you can't reach the switch, unplug the barrel jack from the servo power input.
  4. Do not power the servo rail back on until you understand what happened.

Access tiers — what you can do

SwayForm uses a tiered access model. Your instructor sets your level. Here's what each level means:

  • Tier 1 — View only. You can read code in the hub and observe the robot. You submit code to a team lead for execution.
  • Tier 2 — Run only. You SSH in and can run nodes from the swayform_demos package. You cannot save changes to files.
  • Tier 3 — Edit + run. You have a personal directory in swayform_labs/. You can write and run your own nodes.
  • Tier 4 — Admin. Instructor only. Hardware drivers, ROS 2 config, power management.

Python
#!/usr/bin/env python3
"""
Wave Demo — SwayForm Demo 01
Raises the right arm and performs a smooth three-wave gesture.
Run: ros2 run swayform_demos wave_demo
"""

import math
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState


# ── Helpers ────────────────────────────────────────────────────
def clamp(val, lo, hi):
    """Hard-clamp a value to [lo, hi]. Always call this before publishing."""
    return max(lo, min(hi, val))


def smoothstep(t):
    """S-curve easing. t must be in [0, 1]. Returns value in [0, 1]."""
    t = clamp(t, 0.0, 1.0)
    return t * t * (3.0 - 2.0 * t)


def lerp(a, b, t):
    """Linear interpolation from a to b by factor t."""
    return a + (b - a) * t


def smooth_lerp(a, b, t):
    """Smoothstep-eased interpolation from a to b."""
    return lerp(a, b, smoothstep(t))


# ── Keyframes ──────────────────────────────────────────────────
# Format: (label, duration_seconds, {joint_name: angle_radians})
# Joints not listed hold their previous value — do not snap.

KEYFRAMES = [
    ("raise arm", 1.0, {
        "right_shoulder_pitch": math.radians(60),
        "right_shoulder_roll":  math.radians(-20),
        "right_elbow":          math.radians(-40),
        "right_wrist_yaw":      math.radians(0),
    }),
    ("wave right", 0.5, {
        "right_wrist_yaw": math.radians(35),
    }),
    ("wave left", 0.5, {
        "right_wrist_yaw": math.radians(-35),
    }),
    ("wave right again", 0.5, {
        "right_wrist_yaw": math.radians(35),
    }),
    ("return neutral", 1.2, {
        "right_shoulder_pitch": math.radians(0),
        "right_shoulder_roll":  math.radians(0),
        "right_elbow":          math.radians(0),
        "right_wrist_yaw":      math.radians(0),
    }),
]

# All 17 joints start at neutral (0 radians)
ALL_JOINTS = [
    "neck_yaw", "neck_pitch",
    "right_shoulder_pitch", "right_shoulder_roll",
    "right_elbow", "right_wrist_yaw", "right_wrist_pitch",
    "right_index", "right_thumb",
    "left_shoulder_pitch", "left_shoulder_roll",
    "left_elbow", "left_wrist_yaw", "left_wrist_pitch",
    "left_index", "left_thumb",
    "waist_yaw",
]

PUBLISH_RATE_HZ = 20  # publish 20 times per second


class WaveDemo(Node):
    def __init__(self):
        super().__init__("wave_demo")
        self._pub = self.create_publisher(JointState, "/swayform/joint_targets", 10)

        # Current pose — all joints start at 0
        self._current = {j: 0.0 for j in ALL_JOINTS}

        # Keyframe state
        self._kf_index = 0          # which keyframe we're playing
        self._kf_time  = 0.0        # how long we've been in this keyframe
        self._kf_start = dict(self._current)  # joint values at start of keyframe
        self._done = False

        self._timer = self.create_timer(1.0 / PUBLISH_RATE_HZ, self._tick)
        self.get_logger().info("Starting wave sequence...")

    def _tick(self):
        """Called 20 times per second. Advances the keyframe timeline."""
        if self._done:
            return

        if self._kf_index >= len(KEYFRAMES):
            self.get_logger().info("Sequence complete.")
            self._done = True
            return

        label, duration, targets = KEYFRAMES[self._kf_index]
        self._kf_time += 1.0 / PUBLISH_RATE_HZ

        # Progress from 0.0 to 1.0 through this keyframe
        t = clamp(self._kf_time / duration, 0.0, 1.0)

        # Interpolate every joint that has a target in this keyframe
        for joint in ALL_JOINTS:
            if joint in targets:
                self._current[joint] = smooth_lerp(
                    self._kf_start[joint], targets[joint], t
                )
            # joints not in targets hold their current value — no snapping

        self._publish()

        # Advance to next keyframe when this one is complete
        if t >= 1.0:
            self.get_logger().info(f"Keyframe {self._kf_index + 1} — {label}")
            self._kf_index += 1
            self._kf_time  = 0.0
            self._kf_start = dict(self._current)

    def _publish(self):
        msg = JointState()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.name     = list(self._current.keys())
        msg.position = [clamp(v, math.radians(-170), math.radians(170))
                        for v in self._current.values()]
        self._pub.publish(msg)


def main():
    rclpy.init()
    node = WaveDemo()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()


if __name__ == "__main__":
    main()

Code breakdown

clamp() and smoothstep()

These two functions appear in every single motion node you'll write. clamp() prevents you from sending an angle that would drive the servo into its mechanical stop. smoothstep() converts a linear 0→1 progress value into an S-curve, so joints feel like they have weight — they ease out of a pose and settle into the next one instead of moving at constant speed.

Keyframe structure

Each keyframe is a tuple: (label, duration, targets). The targets dictionary only lists the joints that move in that keyframe. Joints not listed hold their previous value. This is how the wrist can wave (keyframes 2–4) while the shoulder and elbow stay raised from keyframe 1 — they simply aren't in the targets dictionary.

Robot Reality

If you list every joint in every keyframe, all unlisted joints snap to 0 at the start of each keyframe. That's the most common bug in student motion code. Only list joints that should change. Everything else holds automatically because _current persists between ticks.

The 20Hz timer

self.create_timer(1.0 / 20, self._tick) fires the tick function 20 times per second. Inside _tick, we advance a time counter, compute interpolation progress t, update every joint's current value, and publish. When t reaches 1.0 for a keyframe, we advance to the next one and save the current joint positions as the new start.

What to try

  • Change the wrist angle in keyframe 2 from 35° to 50°. Observe how the wave changes. Then try 70° — does anything grind?
  • Change the duration of "raise arm" from 1.0 to 0.3. The arm now snaps up. Change it to 2.5. It drifts up slowly.
  • Add a fourth wave cycle by duplicating keyframes 2 and 3.
  • Add a head nod by including "neck_pitch": math.radians(10) in the "raise arm" keyframe.

#!/usr/bin/env python3
"""
Greeting Demo — SwayForm Demo 02
Subscribes to /swayform/greet (std_msgs/String).
On receipt: head turn + arm raise + TTS + return neutral.
"""

import math
import threading
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState
from std_msgs.msg import String

try:
    import pyttsx3
    TTS_AVAILABLE = True
except ImportError:
    TTS_AVAILABLE = False


def clamp(val, lo, hi):
    return max(lo, min(hi, val))

def smoothstep(t):
    t = clamp(t, 0.0, 1.0)
    return t * t * (3.0 - 2.0 * t)

def smooth_lerp(a, b, t):
    return a + (b - a) * smoothstep(t)


ALL_JOINTS = [
    "neck_yaw", "neck_pitch",
    "right_shoulder_pitch", "right_shoulder_roll",
    "right_elbow", "right_wrist_yaw", "right_wrist_pitch",
    "right_index", "right_thumb",
    "left_shoulder_pitch", "left_shoulder_roll",
    "left_elbow", "left_wrist_yaw", "left_wrist_pitch",
    "left_index", "left_thumb",
    "waist_yaw",
]

NEUTRAL = {j: 0.0 for j in ALL_JOINTS}

GREET_POSE = {
    "neck_yaw":             math.radians(20),
    "neck_pitch":           math.radians(-5),
    "left_shoulder_pitch":  math.radians(55),
    "left_shoulder_roll":   math.radians(15),
    "left_elbow":           math.radians(-30),
    "left_wrist_yaw":       math.radians(0),
}

RATE_HZ = 20


class GreetingDemo(Node):
    def __init__(self):
        super().__init__("greeting_demo")
        self._pub = self.create_publisher(JointState, "/swayform/joint_targets", 10)
        self._sub = self.create_subscription(String, "/swayform/greet", self._on_greet, 10)

        self._current  = dict(NEUTRAL)
        self._target   = dict(NEUTRAL)
        self._start    = dict(NEUTRAL)
        self._anim_t   = 1.0      # 1.0 = animation complete
        self._anim_dur = 1.0
        self._busy     = False     # prevent overlapping greetings

        self._timer = self.create_timer(1.0 / RATE_HZ, self._tick)
        self.get_logger().info("Greeting demo ready. Publish a name to /swayform/greet")

    def _on_greet(self, msg: String):
        if self._busy:
            self.get_logger().warn("Already greeting — ignoring.")
            return
        name = msg.data.strip() or "friend"
        self.get_logger().info(f"Greeting: {name}")
        # Start greeting sequence in a background thread so the timer keeps running
        threading.Thread(target=self._greet_sequence, args=(name,), daemon=True).start()

    def _greet_sequence(self, name: str):
        self._busy = True
        # 1. Move to greet pose over 1.2s
        self._start_anim({**NEUTRAL, **GREET_POSE}, 1.2)
        import time; time.sleep(1.4)
        # 2. Speak (non-blocking via thread-safe call)
        self._speak(f"Hello, {name}!")
        time.sleep(2.0)
        # 3. Return to neutral over 1.5s
        self._start_anim(NEUTRAL, 1.5)
        time.sleep(1.8)
        self._busy = False

    def _start_anim(self, target_pose: dict, duration: float):
        self._start    = dict(self._current)
        self._target   = {**self._current, **target_pose}
        self._anim_dur = duration
        self._anim_t   = 0.0

    def _tick(self):
        if self._anim_t < 1.0:
            self._anim_t = clamp(self._anim_t + (1.0 / RATE_HZ) / self._anim_dur, 0.0, 1.0)
            for j in ALL_JOINTS:
                self._current[j] = smooth_lerp(
                    self._start.get(j, 0.0),
                    self._target.get(j, 0.0),
                    self._anim_t,
                )
            self._publish()

    def _publish(self):
        msg = JointState()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.name     = ALL_JOINTS
        msg.position = [clamp(self._current[j], math.radians(-170), math.radians(170))
                        for j in ALL_JOINTS]
        self._pub.publish(msg)

    def _speak(self, text: str):
        if not TTS_AVAILABLE:
            self.get_logger().info(f"[TTS unavailable] Would say: {text}")
            return
        try:
            engine = pyttsx3.init()
            engine.setProperty("rate", 160)
            engine.say(text)
            engine.runAndWait()
        except Exception as e:
            self.get_logger().warn(f"TTS error: {e}")


def main():
    rclpy.init()
    node = GreetingDemo()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()

if __name__ == "__main__":
    main()

Key concepts introduced

  • Subscription callback — the node doesn't poll. It registers _on_greet and ROS 2 calls it whenever a message arrives on /swayform/greet.
  • Busy flag — self._busy prevents two greetings from overlapping if messages arrive quickly. This pattern appears in every interactive demo.
  • Background thread for sequences — the animation timer must keep running while the greeting sequence sleeps. Threading.Thread lets the sequence sleep without blocking the node's event loop.
  • TTS with try/except — pyttsx3 may not be installed on all configurations. Wrapping it in try/except and logging a fallback message makes the demo resilient.

Demo 03 — Face Tracker

The robot continuously reads the camera stream, detects the largest face in frame using a Haar cascade classifier, and drives the neck joints with a proportional controller so the robot appears to look at whoever is in front of it.
⏱ 25 min
● Intermediate
👁 Uses: camera, neck joints, OpenCV

What the robot does

The node subscribes to /camera/color/image_raw. On each frame it converts the image to grayscale, runs Haar cascade face detection, finds the largest detected face, computes how far the face center is from the image center, and publishes a proportional correction to neck_yaw and neck_pitch. A dead zone of ±5% of frame width prevents micro-jitter when the face is centered.

#!/usr/bin/env python3
"""
Face Tracker — SwayForm Demo 03
Detects faces with Haar cascade and drives neck joints via proportional control.
"""

import math
import cv2
import numpy as np
from cv_bridge import CvBridge
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import Image, JointState


def clamp(val, lo, hi):
    return max(lo, min(hi, val))


# Haar cascade path (pre-installed on the Pi image)
CASCADE_PATH = "/usr/share/opencv4/haarcascades/haarcascade_frontalface_default.xml"

# Proportional gain — how aggressively neck moves toward face
KP_YAW   = 0.6   # horizontal
KP_PITCH = 0.4   # vertical

# Dead zone — normalized, ±5% of frame
DEAD_ZONE = 0.05

# Joint limits for neck
NECK_YAW_MAX   = math.radians(45)
NECK_PITCH_MAX = math.radians(25)

ALL_JOINTS = [
    "neck_yaw", "neck_pitch",
    "right_shoulder_pitch", "right_shoulder_roll",
    "right_elbow", "right_wrist_yaw", "right_wrist_pitch",
    "right_index", "right_thumb",
    "left_shoulder_pitch", "left_shoulder_roll",
    "left_elbow", "left_wrist_yaw", "left_wrist_pitch",
    "left_index", "left_thumb",
    "waist_yaw",
]


class FaceTracker(Node):
    def __init__(self):
        super().__init__("face_tracker")

        self._bridge   = CvBridge()
        self._cascade  = cv2.CascadeClassifier(CASCADE_PATH)
        self._pub      = self.create_publisher(JointState, "/swayform/joint_targets", 10)
        self._img_sub  = self.create_subscription(
            Image, "/camera/color/image_raw", self._on_image, 1
        )

        # Current neck angles (start at 0)
        self._neck_yaw   = 0.0
        self._neck_pitch = 0.0

        if self._cascade.empty():
            self.get_logger().error(f"Could not load cascade from {CASCADE_PATH}")
        else:
            self.get_logger().info("Face tracker ready — waiting for camera frames...")

    def _on_image(self, msg: Image):
        # Convert ROS image to OpenCV BGR, then grayscale for detection
        frame = self._bridge.imgmsg_to_cv2(msg, desired_encoding="bgr8")
        gray  = cv2.cvtColor(frame, cv2.COLOR_BGR2GRAY)
        h, w  = gray.shape

        # Detect faces — scale factor 1.1 means 10% size reduction per pyramid level
        faces = self._cascade.detectMultiScale(
            gray, scaleFactor=1.1, minNeighbors=5, minSize=(60, 60)
        )

        if len(faces) == 0:
            # No face — hold current neck position (don't snap to 0)
            return

        # Pick the largest face (closest person)
        areas = [w_f * h_f for (x, y, w_f, h_f) in faces]
        x, y, fw, fh = faces[int(np.argmax(areas))]

        # Face center in normalized coordinates [-1, 1]
        face_cx_norm = ((x + fw / 2) / w) * 2 - 1   # positive = right of frame
        face_cy_norm = ((y + fh / 2) / h) * 2 - 1   # positive = below center

        # Apply dead zone — only correct if error is outside threshold
        error_x = face_cx_norm if abs(face_cx_norm) > DEAD_ZONE else 0.0
        error_y = face_cy_norm if abs(face_cy_norm) > DEAD_ZONE else 0.0

        # Proportional correction — face right → turn neck right (positive yaw)
        # face below center → tilt neck down (positive pitch)
        self._neck_yaw   = clamp(
            self._neck_yaw   + KP_YAW   * error_x * (1.0 / 30),  # 30Hz image
            -NECK_YAW_MAX, NECK_YAW_MAX
        )
        self._neck_pitch = clamp(
            self._neck_pitch + KP_PITCH * error_y * (1.0 / 30),
            -NECK_PITCH_MAX, NECK_PITCH_MAX
        )

        self._publish()

    def _publish(self):
        msg = JointState()
        msg.header.stamp = self.get_clock().now().to_msg()
        pose = {j: 0.0 for j in ALL_JOINTS}
        pose["neck_yaw"]   = self._neck_yaw
        pose["neck_pitch"] = self._neck_pitch
        msg.name     = list(pose.keys())
        msg.position = list(pose.values())

Demo 04 — Distance Reaction

The robot monitors its ultrasonic distance sensor and changes behavior based on three proximity zones: far (idle), near (prepare posture), and close (full greeting). Uses hysteresis to prevent rapid state toggling.
⏱ 20 min
● Intermediate
📡 Uses: HC-SR04 distance sensor, shoulder + neck

What the robot does

The node subscribes to /swayform/distance (a sensor_msgs/Range message). It maintains a state — idle, prepare, or greet — and transitions between them based on distance thresholds. Hysteresis means entering a state requires crossing one threshold, but exiting requires crossing a different one, preventing jitter.

#!/usr/bin/env python3
"""
Distance Reaction Demo — SwayForm Demo 04
Three proximity zones with hysteresis-based state machine.
"""

import math
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState, Range


def clamp(val, lo, hi):
    return max(lo, min(hi, val))

def smoothstep(t):
    t = clamp(t, 0.0, 1.0)
    return t * t * (3.0 - 2.0 * t)

def smooth_lerp(a, b, t):
    return a + (b - a) * smoothstep(t)


ALL_JOINTS = [
    "neck_yaw", "neck_pitch",
    "right_shoulder_pitch", "right_shoulder_roll",
    "right_elbow", "right_wrist_yaw", "right_wrist_pitch",
    "right_index", "right_thumb",
    "left_shoulder_pitch", "left_shoulder_roll",
    "left_elbow", "left_wrist_yaw", "left_wrist_pitch",
    "left_index", "left_thumb",
    "waist_yaw",
]

# State poses
POSES = {
    "idle":    {j: 0.0 for j in ALL_JOINTS},
    "prepare": {
        **{j: 0.0 for j in ALL_JOINTS},
        "neck_pitch":            math.radians(-8),
        "right_shoulder_pitch":  math.radians(15),
        "left_shoulder_pitch":   math.radians(15),
    },
    "greet": {
        **{j: 0.0 for j in ALL_JOINTS},
        "neck_pitch":            math.radians(-12),
        "right_shoulder_pitch":  math.radians(60),
        "right_shoulder_roll":   math.radians(-15),
        "right_elbow":           math.radians(-30),
        "left_shoulder_pitch":   math.radians(60),
        "left_shoulder_roll":    math.radians(15),
        "left_elbow":            math.radians(-30),
    },
}

# Hysteresis thresholds (meters)
# Enter prepare: distance < 1.0
# Exit prepare (back to idle): distance > 1.2
# Enter greet: distance < 0.5
# Exit greet (back to prepare): distance > 0.65

THRESHOLDS = {
    "idle_to_prepare":    1.0,
    "prepare_to_idle":    1.2,
    "prepare_to_greet":   0.5,
    "greet_to_prepare":   0.65,
}

RATE_HZ = 20


class DistanceReact(Node):
    def __init__(self):
        super().__init__("distance_react")
        self._pub = self.create_publisher(JointState, "/swayform/joint_targets", 10)
        self._sub = self.create_subscription(Range, "/swayform/distance", self._on_range, 10)

        self._state   = "idle"
        self._current = dict(POSES["idle"])
        self._target  = dict(POSES["idle"])
        self._start   = dict(POSES["idle"])
        self._anim_t  = 1.0
        self._anim_dur = 0.8

        self._timer = self.create_timer(1.0 / RATE_HZ, self._tick)
        self.get_logger().info("Distance reaction demo ready.")

    def _on_range(self, msg: Range):
        d = msg.range
        if math.isnan(d) or d <= 0:
            return

        prev = self._state

        # State machine with hysteresis
        if self._state == "idle" and d < THRESHOLDS["idle_to_prepare"]:
            self._state = "prepare"
        elif self._state == "prepare":
            if d > THRESHOLDS["prepare_to_idle"]:
                self._state = "idle"
            elif d < THRESHOLDS["prepare_to_greet"]:
                self._state = "greet"
        elif self._state == "greet" and d > THRESHOLDS["greet_to_prepare"]:
            self._state = "prepare"

        if self._state != prev:
            self.get_logger().info(f"State: {prev} → {self._state}  (d={d:.2f}m)")
            self._start_anim(POSES[self._state], 0.8)

    def _start_anim(self, target: dict, dur: float):
        self._start    = dict(self._current)
        self._target   = dict(target)
        self._anim_t   = 0.0
        self._anim_dur = dur

    def _tick(self):
        if self._anim_t < 1.0:
            self._anim_t = clamp(self._anim_t + (1.0 / RATE_HZ) / self._anim_dur, 0.0, 1.0)
            for j in ALL_JOINTS:
                self._current[j] = smooth_lerp(self._start[j], self._target[j], self._anim_t)
        self._publish()

    def _publish(self):
        msg = JointState()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.name     = ALL_JOINTS
        msg.position = [clamp(self._current[j], math.radians(-170), math.radians(170)) for j in ALL_JOINTS]
        self._pub.publish(msg)


def main():
    rclpy.init()
    node = DistanceReact()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()

if __name__ == "__main__":
    main()

Common mistakes

  • Putting logic inside the class definition but outside a method. All code that runs must be inside a def.

Lab 11 — Read Joint State Feedback

Subscribe to /swayform/joint_states and log what the robot's joints are actually doing — not what you commanded, but what the driver reports back. This is how you verify your commands landed.
⏱ 60 min
🔧 Robot required
📦 Prerequisite: Lab 02

What you will learn

  • How to subscribe to a ROS 2 topic and store data in a class variable
  • The difference between commanded position and reported position (dead-band)
  • How to use a timer to log data separately from the subscription callback
  • Why you can't just read the joint state inside the callback and immediately act on it

Background

When you published to /swayform/joint_targets in Lab 02, you sent a command and hoped for the best. Lab 11 closes the loop: the hardware driver publishes the actual joint positions back on /swayform/joint_states, and your node can subscribe to that to see what really happened.

Robot Reality

Servos don't report position digitally. The driver estimates position from the last command it sent — it does not have encoder feedback on most joints. So "actual position" means "position we commanded, which the servo should be at." The dead-band you'll observe is how close "should be" and "is" actually are — spoiler: good enough for educational robotics.

Power System

The robot has two separate power rails — one for the Pi, one for the servos. Understanding this separation explains most power-related bugs students encounter.

Why two rails?

Servo motors draw large current spikes when they start moving — up to 1.4A per servo for the MG996R. If these spikes were on the same rail as the Pi, they would cause voltage droop and reboot the Pi mid-sequence. The buck converters step 12V down to a stable 6V servo rail and a separate 5V Pi rail, each isolated from the other.

Power sequence

  1. Connect Pi 5V USB-C power first. Wait for full boot (~30 seconds).
  2. Enable servo rail via toggle switch only after the Pi is fully booted and SSH is active.
  3. On shutdown: disable servo rail first, then sudo shutdown now on the Pi.
Robot Reality

If the servo rail was enabled before the Pi finished booting, the PCA9685 driver initializes without knowing the Pi's I²C state and may send garbage PWM values to servos. The robot may twitch or move to unexpected positions. Solution: always wait for full Pi boot before enabling servos.

Hub›Troubleshooting›Servo Twitches

Flowchart: Servo Twitches or Jitters

Continuous twitching without a code command is always electrical. Twitching during motion is usually a code timing issue.
If a servo is hot to the touch — cut servo power immediately. A stalling servo draws full current continuously and will damage itself in minutes.
