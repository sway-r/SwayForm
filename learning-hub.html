Learning Hub / What SwayForm Teaches

What SwayForm Teaches

SwayForm is built to make robotics concrete. Every concept students encounter connects to something the robot physically does. You are not learning robotics on a simulator or through slides — you are writing code that moves hardware.

Python through physical behavior

Students write real Python. Not toy exercises — actual scripts that send motor commands, read camera data, respond to sensors, and chain behaviors. The feedback loop is physical: if your code is wrong, the robot does the wrong thing, and you can see it immediately.

ROS 2 thinking

SwayForm is built around ROS 2-style architecture. Students learn what a node is by writing one. They learn what a topic is by publishing to one. They learn what a subscriber is by building a behavior that reacts to camera data. The goal is not to memorize definitions — it is to understand why a system like ROS exists and what problem it solves.

Concepts covered through the demo and lab programs:

  • Nodes — programs that run independently and communicate with others
  • Topics — named channels where nodes send and receive data
  • Publishers — code that sends data on a topic
  • Subscribers — code that receives data from a topic
  • Services — request-response communication between nodes
  • Launch files — scripts that start multiple nodes together

Servo control and joint motion

Students learn that robot motion is joint angles, not simple high-level commands. You specify where a joint should go in radians, and the servo controller moves it there. Students develop an intuition for what values are safe, why limits exist, and how timing affects how smooth a motion feels.

Computer vision with RealSense

The Intel RealSense camera gives SwayForm both color and depth data. Labs and demos teach students how camera data can be used as a trigger for robot behavior — detecting when someone is present, finding a target zone, or mapping a visual position to a head angle. The hub is honest about what works as a classroom demo and what would require more advanced computer vision.

Timing, sequencing, and motion locking

Many behaviors require careful timing. Students learn why a wave looks unnatural at the wrong speed, why two behaviors cannot safely command the same joint simultaneously, and why returning to a safe idle pose matters. These are practical lessons about real robotics constraints.

Debugging through the terminal

Students read terminal output, understand error messages, and fix problems themselves. There is no visual debugger with a "fix" button. The terminal is the interface, and reading it is part of learning.

Honest expectation

SwayForm does not promise that students will become professional robotics engineers in a semester. The goal is to give students a real, hands-on experience with a physical robot system so that further study in robotics, Python, or embedded systems feels grounded in something they already understand.

Learning Hub / How Students Use This Hub

How Students Use This Hub

The typical student flow starts with a provided demo, moves into reading the code, then into making small edits, and finally into completing guided labs.

The standard flow

  1. Open the Learning Hub (you are here).
  2. Connect to the robot through VS Code and SSH (see Setup).
  3. Run a provided demo to see the robot do something.
  4. Open the demo's code walkthrough in the hub and read it.
  5. Make one small modification from the "Try changing this" list.
  6. Open the corresponding lab for that topic.
  7. Complete the lab using the starter code and step-by-step guide.
  8. Answer the reflection question and attempt the extension challenge.

Self-paced vs class-led

The hub is designed so students can move through it independently. Labs are self-contained — you do not need to have completed the previous lab to start a new one, although they do build on each other conceptually.

In a class setting, a teacher might assign one lab per session. In a club setting, students can move faster and use the extension challenges to go further.

What to do when something breaks

Check the Troubleshooting section first. Most first-time problems (SSH not connecting, command not found, robot not moving) have clear causes and documented fixes. Reading terminal output carefully usually reveals the problem before you need to ask anyone.

Learning Hub / Safety Notes

Safety Notes

SwayForm is designed for classroom use and is built with safe joint limits in the motion software. These notes help you get the most out of the robot without damaging it or surprising someone in the room.

Safety

Keep hands and objects clear of the robot's arms and hands while a demo or script is running. The robot does not know you are there unless a camera behavior is specifically active.

General rules

  • Do not manually force the robot's arms into a position while a script is running. If a joint is resisting, stop the script first.
  • Keep objects for tabletop demos light. The robot is not designed to lift heavy items.
  • Stop the running script before repositioning objects near the robot.
  • Always return the robot to a neutral or idle pose before powering off.
  • When working with base rotation, make sure the cable slack allows the turn direction you are commanding. Do not spin the base continuously in one direction.

Joint limits

Every servo joint on SwayForm has a software-enforced safe range. The motion software will clamp commanded angles to these limits before sending them to the hardware. You cannot easily damage the robot by sending bad angle values — the system catches this. However, rapidly switching between extreme positions can put stress on the motors, so smooth, gradual motions are always preferred.

Dollar bill demo note

The Dollar Bill Snack Exchange demo is a classroom interaction demo only. It does not process real payments and does not validate currency. It is designed to demonstrate sequenced manipulation and human-robot interaction in an educational context.

Learning Hub / Setup / Getting Started

Getting Started

From power-on to running your first demo in about 10 minutes. Follow these steps in order your first time.

Step 1 — Power on SwayForm

Flip the main power switch on the robot base. Wait about 30 seconds for the Raspberry Pi to finish booting. The system is ready when the status indicator shows steady (not blinking).

Step 2 — Connect to the same network

Make sure your laptop is connected to the same Wi-Fi network as the robot, or connected via a direct Ethernet link. SwayForm uses a local hostname — you do not need internet access.

Step 3 — Open VS Code

Open Visual Studio Code on your laptop. Install the Remote - SSH extension if you do not have it already.

Step 4 — Connect via SSH

Open the VS Code command palette (Ctrl+Shift+P / Cmd+Shift+P) → "Remote-SSH: Connect to Host" → enter:

Terminal
ssh swayform@swayform.local

Enter the password when prompted. You should see a terminal prompt like swayform@swayform:~$.

Step 5 — Navigate to the workspace

Terminal
cd ~/ros2_ws

Step 6 — Source the workspace

This step makes all SwayForm ROS 2 commands available in your terminal. You must do this every time you open a new terminal session.

Terminal
source install/setup.bash

Step 7 — Run the wave demo

Terminal
ros2 run swayform_demos wave_demo

The robot should raise its right arm and wave three times, then return to idle. If nothing happens, check the Troubleshooting section.

Step 8 — Stop the demo safely

Press Ctrl+C in the terminal to stop the script. The robot will finish its current motion and return to idle if the script includes a cleanup function.

Step 9 — Open the first lab

You are ready. Open Lab 01 in the sidebar to start your first guided exercise.

Pro tip

Add source ~/ros2_ws/install/setup.bash to your ~/.bashrc so you do not have to source manually every session.

Learning Hub / Setup / VS Code + SSH

VS Code + SSH Setup

SSH lets your laptop talk to the robot over the network. VS Code's Remote-SSH extension makes the robot's filesystem feel like a local project — you can browse files, edit code, and run a terminal all in one window.

What SSH means

SSH (Secure Shell) is a way to open a terminal on a remote computer — in this case, the Raspberry Pi inside SwayForm — from your own laptop. Once connected, commands you type run on the robot, not on your laptop. Your code editor can also open and save files on the robot directly.

Why students use VS Code

  • Full code editor with syntax highlighting and autocomplete
  • Integrated terminal for running commands on the robot
  • File browser to navigate the robot's filesystem
  • Works on Windows, Mac, and Linux
  • No need to copy files back and forth — you edit directly on the robot

Required VS Code extension

Install the Remote - SSH extension from the VS Code Extensions panel (Ctrl+Shift+X). Search for "Remote SSH" and install the one published by Microsoft.

Connecting for the first time

  1. Press Ctrl+Shift+P to open the command palette
  2. Type "Remote-SSH: Connect to Host" and press Enter
  3. Enter swayform@swayform.local
  4. Enter the password when prompted
  5. VS Code will open a new window connected to the robot
  6. Click "Open Folder" and navigate to /home/swayform/ros2_ws

Where files live

swayform_demos — official demo examples provided by SwayForm. These are your reference code. Read them, study them, but avoid editing them directly. If you want to experiment, copy the file to the labs folder first.

swayform_labs — your working folder. All lab starter code lives here. Edits you make in this folder are safe and persistent.

Note

Changes saved in VS Code Remote-SSH are saved directly on the robot. There is no separate "upload" step. If you disconnect VS Code, your changes are already there.

Learning Hub / Setup / Stopping a Motion Safely

Stopping a Motion Safely

Press Ctrl+C in the terminal to stop any running script. If the script includes a safe_pose('idle') call at the end, the robot will finish its current motion and return to a safe position before stopping.

If the robot stops mid-motion and stays in an awkward pose, you can manually run:

Terminal
ros2 run swayform_demos reset_pose

This moves all joints back to the neutral idle position.

Safety

Never pull the robot's arms into a different position while a script is running. Always stop the script first, then reposition if needed.

Learning Hub / Demo Code Library / Demo 01: Wave

Demo 01: Wave

Difficulty Beginner Time ~10 min Status Ready

The robot raises its right arm and waves three times using a timed sequence of servo commands. This is the simplest motion demo — no camera, no sensors, just clean joint control.

What it does

The script moves to a neutral starting pose, raises the right arm to wave height, then alternates between a higher and lower position three times before returning to idle. Each movement uses a timed duration to control how fast the joint moves.

What students learn

  • How to define joint target angles
  • How motion duration affects speed and smoothness
  • The importance of starting and ending in a safe pose
  • How to run a repeated motion loop
  • What a "safe limit" means in practice

Hardware used

  • Right shoulder servo (pitch and yaw)
  • Right elbow servo (flex)
  • Motion controller node

Run command

Terminal
ros2 run swayform_demos wave_demo

Code walkthrough

~/ros2_ws/src/swayform_demos/wave_demo.py
python
# wave_demo.py — SwayForm Demo 01
import time
from swayform.client import MotionClient

def main():
    robot = MotionClient()
    robot.connect()

    # Always move to a safe neutral pose before starting
    robot.safe_pose('neutral')
    time.sleep(1.0)

    # Define the two wave positions (angles in radians)
    WAVE_UP   = {'right_shoulder_pitch': -1.2, 'right_elbow_flex': 0.5}
    WAVE_DOWN = {'right_shoulder_pitch': -0.7, 'right_elbow_flex': 0.2}

    # Wave three times
    for _ in range(3):
        robot.move_joint_group(WAVE_UP, duration=0.6)
        robot.wait(0.5)
        robot.move_joint_group(WAVE_DOWN, duration=0.5)
        robot.wait(0.4)

    # Return to idle — always do this before ending a script
    robot.safe_pose('idle')
    robot.disconnect()

if __name__ == '__main__':
    main()

Line-by-line explanation

  • MotionClient() — creates a connection to the SwayForm motion node running on the robot.
  • safe_pose('neutral') — moves all joints to a known safe starting position. Always do this at the start of a script.
  • WAVE_UP / WAVE_DOWN — dictionaries mapping joint names to target angles. Negative values for shoulder_pitch raise the arm upward.
  • move_joint_group(target, duration) — sends the target angles. The duration parameter controls how long the movement takes. Shorter duration = faster, less smooth.
  • wait() — pauses before the next command so motions do not overlap.
  • safe_pose('idle') — returns robot to relaxed idle before disconnecting.

Why delays matter

If you remove the wait() calls, the next motion command starts before the first one finishes. This can cause jerky motion or the robot trying to go to two places at once. Small delays give each motion time to complete before the next begins.

Why safe limits matter

The motion software clamps any angle you send to the safe range for that joint. If you accidentally set right_shoulder_pitch to -3.0 when the limit is -1.5, the system sends -1.5 instead. You cannot easily damage the robot by sending a bad value, but you might not get the motion you expected if you are outside the valid range.

Try changing this

  • Change range(3) to range(5) for 5 wave cycles
  • Change the duration values — try 0.3 for a fast wave and 1.2 for a slow one
  • Change right_shoulder_pitch to left_shoulder_pitch to wave with the left arm
  • Add 'neck_yaw': 0.3 to WAVE_UP so the robot also turns its head while waving
Safety

Keep hands clear of the arm while the script runs. The arm moves without sensing obstacles.

Demo 02: Vision Handshake

Difficulty Beginner+ Time ~15 min Status Ready

The robot uses the RealSense camera to detect that a person is nearby. When presence is detected, it extends one arm into a handshake position, holds briefly, then returns to neutral. This demo teaches how perception can trigger physical behavior.

Honest note

This is a vision-assisted demo using presence detection, not precise hand pose tracking. It detects that someone is in the camera's front zone — not the exact position of their hand. This is appropriate and realistic for a classroom demo.

What it does

The script starts the RealSense camera stream, moves to neutral, then waits. When a person is detected within a set zone in front of the robot, it sends the arm into a handshake pose and holds it there for a few seconds before returning to neutral.

What students learn

  • Starting and using the RealSense camera stream
  • Checking a detection condition in a loop
  • Triggering robot motion from a perception event
  • Motion locking — one behavior runs, others wait
  • Why robots should move conservatively near people

Hardware used

  • Intel RealSense camera
  • Right shoulder and elbow servos
  • Motion controller node

Run command

Terminal
ros2 run swayform_demos vision_handshake

Code walkthrough

~/ros2_ws/src/swayform_demos/vision_handshake.py
python
# vision_handshake.py — SwayForm Demo 02
import time
from swayform.client import MotionClient
from swayform.perception import RealSenseStream

HANDSHAKE_POSE = {
    'right_shoulder_pitch': -0.6,
    'right_shoulder_yaw':    0.3,
    'right_elbow_flex':      0.8,
}

def main():
    robot = MotionClient()
    robot.connect()

    camera = RealSenseStream()
    camera.start()

    robot.safe_pose('neutral')
    print("Waiting for user presence in front zone...")

    while True:
        frame = camera.get_frame()
        # Detect a person in the front zone with moderate confidence
        if frame.person_detected(zone='front', min_confidence=0.6):
            print("User detected — initiating handshake pose")

            # Extend arm into handshake position
            robot.move_joint_group(HANDSHAKE_POSE, duration=1.2)
            robot.wait(2.5)    # Hold position for 2.5 seconds

            # Return to neutral before detecting again
            robot.safe_pose('neutral')
            robot.wait(1.0)
            break              # End demo after one handshake

    camera.stop()
    robot.disconnect()

if __name__ == '__main__':
    main()

Key points

  • RealSenseStream — starts the camera and provides frame objects you can query.
  • person_detected(zone='front') — returns True when a person is detected in the camera's front detection zone. The exact detection method depends on the SwayForm perception layer.
  • min_confidence=0.6 — only trigger if detection confidence is above 60%. Prevents false triggers from brief noise.
  • The while True loop keeps checking for presence. In a real classroom scenario you might add a timeout so it does not wait forever.
  • The break ends the demo after one handshake. You could remove it for a continuous interactive loop.

Try changing this

  • Change robot.wait(2.5) to a longer value to hold the handshake position longer
  • Add a head nod: robot.move_joint_group({'neck_pitch': 0.2}, duration=0.5) during the hold
  • Remove the break to make the robot do a handshake with every person who walks by
  • Add a timeout: if no one is detected in 30 seconds, exit the loop
Learning Hub / Demo Code Library / Demo 03: Look and Point

Demo 03: Look and Point

Difficulty Beginner+ Time ~15 min Status Ready

The robot detects a target in its camera frame, turns its head toward it, then raises and points one arm in the target's direction. This demo shows how a position in camera space can drive two separate robot behaviors in sequence.

What it does

The script captures a camera frame and finds a primary target (a person, colored object, or center-frame reference depending on setup). It maps the target's horizontal position to a head yaw angle, turns the head, then moves the arm into a pointing gesture. After holding briefly, it returns to idle. The robot looks before it points.

What students learn

  • Reading camera frame coordinates
  • Mapping a pixel position to a joint angle
  • Head yaw and pitch control
  • Sequencing two behaviors (look, then point)
  • Why robots should look before pointing (behavior ordering)

Hardware used

  • Intel RealSense camera
  • Neck yaw and pitch servos
  • Right shoulder and elbow servos

Run command

Terminal
ros2 run swayform_demos look_and_point

Code walkthrough

~/ros2_ws/src/swayform_demos/look_and_point.py
python
# look_and_point.py — SwayForm Demo 03
import time
from swayform.client import MotionClient
from swayform.perception import RealSenseStream

def map_x_to_yaw(target_x, frame_width):
    """Convert horizontal pixel position to a head yaw angle."""
    center = frame_width / 2
    # Normalized offset: -1.0 (left) to +1.0 (right)
    offset = (target_x - center) / center
    # Scale to yaw range. Negative = turn right (camera convention)
    return {'neck_yaw': offset * -0.55}

POINT_POSE = {
    'right_shoulder_pitch': -0.5,
    'right_shoulder_yaw':    0.1,
    'right_elbow_flex':      0.1,
}

def main():
    robot = MotionClient()
    robot.connect()
    camera = RealSenseStream()
    camera.start()

    robot.safe_pose('neutral')

    frame = camera.get_frame()
    target = frame.get_primary_target()   # Returns None if nothing detected

    if target:
        # Step 1 — look toward target
        head_angles = map_x_to_yaw(target.x, frame.width)
        robot.move_joint_group(head_angles, duration=0.8)
        robot.wait(0.6)

        # Step 2 — point arm toward target
        robot.move_joint_group(POINT_POSE, duration=0.7)
        robot.wait(1.5)

        # Step 3 — return to idle
        robot.safe_pose('idle')
    else:
        print("No target found in frame.")
        robot.safe_pose('idle')

    camera.stop()
    robot.disconnect()

if __name__ == '__main__':
    main()

Key concepts

  • map_x_to_yaw() — converts a horizontal pixel position (0 to frame_width) into a yaw angle. The normalized offset centers the range and scales it to the safe neck yaw range.
  • get_primary_target() — returns the most prominent detected object in the frame. What counts as "primary" depends on the perception configuration.
  • Sequence ordering matters: looking before pointing feels natural and gives the robot a moment to orient before committing to the gesture.

Try changing this

  • Change the scale factor 0.55 in map_x_to_yaw to change how far the head turns for a given target offset
  • Use left_shoulder_pitch and left_elbow_flex to point with the left arm
  • Add a short pause after looking before pointing: robot.wait(1.0)
  • After pointing, have the robot turn its head back to center before returning to idle

Demo 04: Rock Paper Scissors

Difficulty Intermediate Time ~20 min Status Ready

The robot plays rock-paper-scissors with a student. It randomly selects a choice, moves its hand into the matching pose, reads the student's input, and announces the result. This demo introduces pose presets, branching logic, and a game loop.

Two modes

The current demo uses keyboard mode: the student types their choice. A future version can use gesture recognition from the RealSense camera. The code structure already supports extending to vision-based input.

Run command

Terminal

Code walkthrough

~/ros2_ws/src/swayform_demos/rock_paper_scissors.py
python
# rock_paper_scissors.py — SwayForm Demo 04
import random, time
from swayform.client import MotionClient

# Hand pose presets for each choice
POSES = {
    'rock':     {'right_hand_grip': 0.9, 'right_index_ext': 0.1, 'right_middle_ext': 0.1},
    'paper':    {'right_hand_grip': 0.0, 'right_index_ext': 1.0, 'right_middle_ext': 1.0},
    'scissors': {'right_hand_grip': 0.5, 'right_index_ext': 1.0, 'right_middle_ext': 0.0},
}

def decide_winner(robot_choice, user_choice):
    """Return 'robot', 'user', or 'tie'."""
    beats = {'rock': 'scissors', 'scissors': 'paper', 'paper': 'rock'}
    if robot_choice == user_choice:
        return 'tie'
    return 'robot' if beats[robot_choice] == user_choice else 'user'

def main():
    robot = MotionClient()
    robot.connect()
    robot.safe_pose('neutral')

    # Robot picks secretly
    robot_pick = random.choice(['rock', 'paper', 'scissors'])

    # Student inputs their choice
    user_pick = input("Your choice (rock / paper / scissors): ").strip().lower()

    print("3... 2... 1... Shoot!")
    time.sleep(1.0)

    # Robot reveals its choice
    robot.move_joint_group(POSES[robot_pick], duration=0.4)
    robot.wait(0.4)

    # Announce result
    result = decide_winner(robot_pick, user_pick)
    print(f"Robot: {robot_pick}   |   You: {user_pick}")
    print(f"Result: {result.upper()}")

    robot.wait(2.5)
    robot.safe_pose('idle')
    robot.disconnect()

if __name__ == '__main__':
    main()

Key concepts

  • POSES dictionary — maps each game choice to a set of hand joint angles. Each value is between 0.0 (fully open) and 1.0 (fully closed/extended).
  • random.choice() — picks one item from a list randomly. This is how the robot makes its decision.
  • decide_winner() — pure Python logic. No robot hardware involved. This is just a function that returns who won based on the standard rules.
  • input() — pauses the script and waits for keyboard input from the student. In a vision version, this would be replaced by a camera-based gesture read.

Demo 05: Dollar Bill Snack Exchange

Difficulty Intermediate Time ~20 min Status Ready
Classroom demo only

This demo assumes any object placed in front of the robot is a $1 bill. It does not process real payments, validate currency, or make any financial transaction. For classroom interaction and state machine education only.

A classroom demo where a student places a bill in front of the robot. The robot detects it (or takes a keyboard trigger), moves the bill aside, then picks up or pushes forward a snack packet. The full behavior is controlled by a state machine — the most complex concept in this demo set.

What it does

The robot waits for a bill-detection trigger (camera zone or keyboard input), accepts the bill, moves it to the side, reaches for a snack item placed on the table nearby, and presents it to the student. Each step is a named state in a state machine.

State machine

The full behavior runs through these states in order:

  • IDLE — robot is at neutral, waiting to begin
  • WAIT_FOR_BILL — camera watching the bill zone, or waiting for keyboard trigger
  • ACCEPT_BILL — arm moves to bill position and hand closes around it
  • PLACE_BILL_ASIDE — arm sweeps bill to the side zone, hand opens
  • PICK_SNACK — arm moves to snack position, hand grips lightly
  • HAND_SNACK — arm presents snack to student, hand opens
  • RETURN_HOME — arm returns to idle, session ends

Run command

Terminal
ros2 run swayform_demos dollar_snack_exchange

Code walkthrough

~/ros2_ws/src/swayform_demos/dollar_snack_exchange.py
python
# dollar_snack_exchange.py — SwayForm Demo 05
# Classroom demo only. Not real payment processing.
import time
from swayform.client import MotionClient
from swayform.perception import RealSenseStream

# Arm pose for each state
ACCEPT_POSE  = {'right_shoulder_pitch': -0.4, 'right_elbow_flex': 0.9, 'right_hand_grip': 0.0}
GRASP_POSE   = {'right_hand_grip': 0.7}
ASIDE_POSE   = {'right_shoulder_pitch': -0.2, 'right_shoulder_yaw': -0.8, 'right_elbow_flex': 0.4}
SNACK_REACH  = {'right_shoulder_pitch': -0.3, 'right_shoulder_yaw': 0.2, 'right_elbow_flex': 0.6}
PRESENT_POSE = {'right_shoulder_pitch': -0.5, 'right_elbow_flex': 0.85, 'right_hand_grip': 0.0}

def main():
    robot = MotionClient()
    robot.connect()
    camera = RealSenseStream()
    camera.start()

    state = 'IDLE'
    robot.safe_pose('neutral')

    while state != 'DONE':

        if state == 'IDLE':
            print("Ready. Place a bill in the detection zone.")
            state = 'WAIT_FOR_BILL'

        elif state == 'WAIT_FOR_BILL':
            frame = camera.get_frame()
            if frame.object_in_zone('bill_zone'):
                print("Bill detected.")
                state = 'ACCEPT_BILL'
            else:
                time.sleep(0.2)   # Check again shortly

        elif state == 'ACCEPT_BILL':
            robot.move_joint_group(ACCEPT_POSE, duration=1.0)
            robot.wait(0.5)
            robot.move_joint_group(GRASP_POSE, duration=0.5)
            robot.wait(0.4)
            state = 'PLACE_BILL_ASIDE'

        elif state == 'PLACE_BILL_ASIDE':
            robot.move_joint_group(ASIDE_POSE, duration=1.0)
            robot.wait(0.4)
            robot.set_hand_pose('open')
            robot.wait(0.3)
            state = 'PICK_SNACK'

        elif state == 'PICK_SNACK':
            robot.move_joint_group(SNACK_REACH, duration=1.0)
            robot.wait(0.3)
            robot.set_hand_pose('pinch')
            robot.wait(0.5)
            state = 'HAND_SNACK'

        elif state == 'HAND_SNACK':
            robot.move_joint_group(PRESENT_POSE, duration=1.0)
            robot.wait(2.0)
            robot.set_hand_pose('open')
            state = 'RETURN_HOME'

        elif state == 'RETURN_HOME':
            robot.safe_pose('idle')
            state = 'DONE'

    camera.stop()
    robot.disconnect()
    print("Exchange complete.")

if __name__ == '__main__':
    main()

Why state machines

A state machine makes the behavior readable and debuggable. Instead of one long sequence of commands, each named state does exactly one thing before deciding what comes next. If the demo breaks at the snack pickup step, you know exactly which state to look at.

State machines also make it easy to add new behavior. Want to add a timeout on WAIT_FOR_BILL? Add a timer check in that one state. The rest of the code does not change.

Try changing this

  • Change the snack pose to match a different table layout
  • Add a timeout in WAIT_FOR_BILL: if no bill after 30 seconds, return to idle
  • Add a second snack option with an if/else branch in PICK_SNACK
  • Add a wave at the end after the exchange completes

# Lab 09: Behavior Priority and Motion Locking
import time, threading
from swayform.client import MotionClient

motion_lock = threading.Lock()

def run_behavior(robot, name, pose, duration, priority):
    if motion_lock.locked():
        print(f"[{name}] blocked — motion lock held")
        return
    with motion_lock:
        print(f"[{name}] starting (priority {priority})")
        robot.move_joint_group(pose, duration=duration)
        robot.wait(duration + 0.2)
        print(f"[{name}] done")

def main():
    robot = MotionClient()
    robot.connect()
    robot.safe_pose('neutral')

    # TODO: Try running two behaviors and watch how the lock prevents overlap
    WAVE  = {'right_shoulder_pitch': -1.0, 'right_elbow_flex': 0.5}
    POINT = {'right_shoulder_pitch': -0.4, 'right_elbow_flex': 0.1}

    t1 = threading.Thread(target=run_behavior, args=(robot, 'Wave',  WAVE,  1.2, 1))
    t2 = threading.Thread(target=run_behavior, args=(robot, 'Point', POINT, 0.8, 2))

    t1.start()
    time.sleep(0.1)   # Small delay so Wave starts first
    t2.start()

    t1.join()
    t2.join()

    robot.safe_pose('idle')
    robot.disconnect()

if __name__ == '__main__':
    main()

Steps

  1. Run the script. Observe which behavior runs and which is blocked.
  2. Remove the time.sleep(0.1). Does Point sometimes run instead of Wave?
  3. Change the delay to 2.0 seconds so Wave finishes before Point starts. What happens now?
  4. Read the terminal output carefully — can you trace exactly which behavior ran at each moment?

Learning Hub/Reference/ROS 2 Concepts

ROS 2 Concepts

ROS 2 (Robot Operating System 2) is the software layer that connects all parts of the SwayForm system. Understanding a few key concepts helps you understand why the code is structured the way it is.

Node

A node is a single program that does one job. On SwayForm, the motion node manages all joint commands. The camera node publishes image data. A behavior script you write is also a node — it runs independently and communicates with the others.

Think of nodes like workers in a factory. Each one has a specific task and communicates through a shared system.

Topic

A topic is a named channel where nodes send and receive data. For example, the motion node listens on the topic /swayform/joint_targets. Any node that publishes to that topic can command a joint to move. SwayForm's camera node might publish on /swayform/camera/color/image_raw.

Publisher

A publisher sends data on a topic. When your behavior script sends a joint command, it uses a publisher to put that command on the /joint_targets topic. The motion node is listening, receives the command, and moves the joint.

Subscriber

A subscriber receives data from a topic. The motion node subscribes to /joint_targets. A behavior that reacts to camera data subscribes to the camera topic and receives new frames as they arrive.

How a wave script fits in

A wave script connects to the motion node and publishes joint angle targets on the /joint_targets topic. The motion node (which is always running when SwayForm is on) subscribes to that topic, reads the angles, and sends them to the servo controllers. The servo controllers move the physical joints.

So the chain is: your script → topic → motion node → servo controller → joint movement.

Motion lock

If two behavior scripts publish to the same joint topic at the same time, the result is unpredictable. The motion node uses a locking mechanism to ensure only one behavior can control a joint group at a time. If your script tries to command a joint that is already locked by another script, it is either rejected or queued.

Launch file

A launch file is a script that starts multiple nodes at once. When SwayForm boots, a launch file starts the motion node, camera node, and other background services automatically. You do not typically need to write launch files in the labs, but you will see them referenced in the workspace.

Learning Hub/Reference/Motion Node

Motion Node

The motion node is the core of SwayForm's movement system. It runs continuously on the robot, receives joint targets from behavior scripts, enforces safe limits, and controls the servo hardware.

What it does

  • Subscribes to joint target commands from behavior scripts
  • Clamps all commanded angles to the safe limits for each joint
  • Interpolates smoothly from the current position to the target
  • Publishes actual joint positions so scripts can read feedback
  • Manages motion locking to prevent conflicting commands

Topics

  • /swayform/joint_targets — input: behavior scripts publish here
  • /swayform/joint_states — output: actual joint positions published here
  • /swayform/motion_lock — status: which behavior (if any) holds the lock

MotionClient

The MotionClient class in the SwayForm Python library wraps all of this communication. When you call robot.move_joint_group(), the client publishes to /joint_targets and manages the locking handshake for you.

Learning Hub/Reference/Servo Mapping

Servo Mapping

SwayForm uses named joint identifiers in its motion API. This page explains how joint names correspond to physical parts of the robot.

Naming convention

Joint names follow the pattern: [side]_[body_part]_[axis]

  • right_shoulder_pitch — raises/lowers the right arm
  • right_shoulder_yaw — rotates the right arm forward/back
  • right_elbow_flex — bends the right elbow
  • right_wrist_roll — rotates the right wrist
  • right_hand_grip — overall hand close (0=open, 1=closed)
  • right_index_ext — index finger extension
  • right_middle_ext — middle finger extension
  • neck_yaw — head left/right rotation
  • neck_pitch — head up/down tilt
  • base_yaw — rotating base left/right

Left-side joints follow the same naming pattern with left_ prefix.

Angle conventions

  • All angles are in radians
  • Positive values generally correspond to one direction, negative to the other
  • Zero (0.0) is typically the neutral/center position for that joint
  • For hand_grip and finger extension values: 0.0 = fully open, 1.0 = fully closed/extended
Learning Hub/Reference/Hardware & RealSense

Hardware & Motion

SwayForm's physical system is controlled by software running on an onboard Raspberry Pi. Understanding how code connects to hardware helps you debug problems and design better behaviors.

Raspberry Pi

The Raspberry Pi is the brain of SwayForm. It runs the ROS 2 nodes, the motion node, the camera driver, and all student scripts. When you SSH into the robot, you are connecting to the Raspberry Pi. Your code runs there, not on your laptop.

Servo controllers

Multiple servo motors control SwayForm's joints. A servo controller board sits between the Raspberry Pi and the physical servos — it receives position commands from the motion node and drives the motors to the target angle. The controller handles the low-level PWM signals. You do not interact with it directly in the labs.

Intel RealSense camera

The RealSense camera provides both an RGB color image and a depth map at the same time. The color image lets you detect people, objects, and features. The depth map gives you actual distance measurements — so you can know not just that something is in the frame, but how far away it is.

In the SwayForm demos and labs, the RealSense is used through the RealSenseStream helper class. It abstracts the camera driver and gives you clean frame objects to query.

Arms, hands, head, base

SwayForm's body is divided into controllable subsystems. Each subsystem has its own set of joints. All of them are accessible through the same MotionClient interface — you just specify which joints you want to move by name.

Why behaviors should use smooth transitions

Jumping instantly from one joint angle to another can create mechanical shock that stresses the servos. The motion node's interpolation smooths commands over the requested duration, reducing stress and making the robot's movements look intentional. Always use a reasonable duration — avoid 0.0.

Learning Hub/Reference/Troubleshooting

Troubleshooting

Most first-time problems have straightforward causes. Click any symptom to see the likely cause and fix.

Cannot SSH into the robot+
Likely cause
Laptop and robot are not on the same network, or the robot has not finished booting.
Fix
Check that both devices are on the same Wi-Fi. Wait 45 seconds after power-on before connecting. Try ssh swayform@<IP address> instead of the hostname if swayform.local does not resolve.
VS Code cannot connect+
Likely cause
Remote-SSH extension is not installed, or the hostname is wrong.
Fix
Install the "Remote - SSH" extension from Microsoft in VS Code Extensions. Make sure you are using swayform@swayform.local as the host string.
Demo command not found+
Likely cause
You forgot to source the workspace in this terminal session.
Fix
Run: source ~/ros2_ws/install/setup.bash — then try the command again. Do this every time you open a new terminal.
Robot does not move when demo runs+
Likely cause
The motion node is not running, or another script holds the motion lock.
Fix
Check if any other scripts are running in other terminal tabs. Kill them with Ctrl+C. If the motion node crashed, it should restart automatically; wait 10 seconds and try again.
Camera not detected+
Likely cause
RealSense camera node is not running, or the USB connection to the Raspberry Pi is loose.
Fix
Check the physical USB connection between the camera and the Raspberry Pi. Check if the camera node is listed when you run ros2 node list. If not, it may need to be restarted.
Script ends but robot stays in a raised-arm position+
Likely cause
The script was interrupted before the safe_pose('idle') call at the end.
Fix
Run ros2 run swayform_demos reset_pose to return all joints to neutral. In your own scripts, use try/finally to ensure the reset always runs even if an error occurs.
Permission denied when running a script+
Likely cause
The file does not have execute permission, or you are trying to run a file in a read-only location.
Fix
Use ros2 run rather than running the file directly with python3. If you need to run directly: chmod +x filename.py and make sure you are in the labs folder.
I edited the wrong file (modified a demo instead of a lab)+
Likely cause
You opened and edited a file in swayform_demos/ instead of swayform_labs/.
Fix
Run git checkout HEAD -- src/swayform_demos/filename.py inside ~/ros2_ws to restore the original. From now on, copy demo files to the labs folder before editing them.
Learning Hub/Reference/Glossary

Glossary

Quick definitions for terms used throughout the Learning Hub.

ROS 2
Robot Operating System 2. A framework for building robot software. It provides the tools for nodes, topics, messaging, and launch files that SwayForm uses to connect all its parts.
Node
A single program in ROS 2 that does one job. The motion node manages joints. The camera node publishes image data. Your behavior script is also a node.
Topic
A named channel in ROS 2 where nodes send and receive data. For example: /swayform/joint_targets. Any node can publish to or subscribe from a topic.
Publisher
A piece of code that sends data on a topic. When your script sends a motion command, it uses a publisher.
Subscriber
A piece of code that receives data from a topic. The motion node subscribes to joint target commands. A behavior that reacts to camera data subscribes to the camera topic.
Servo
A small motor that can be commanded to a specific angle and hold it. SwayForm's joints are each controlled by one or more servos.
Joint
A moveable connection between two parts of the robot. The shoulder, elbow, wrist, neck, and fingers are all joints. Each joint is controlled by one or more servos.
Pose
A named or defined configuration of joint angles. "Neutral pose" means all joints are in a safe resting position. A custom pose is just a dictionary of joint names and target angles.
RealSense
The Intel RealSense camera used on SwayForm. It provides both color (RGB) and depth images simultaneously. Used for presence detection, zone tracking, and basic vision behaviors.
SSH
Secure Shell. A way to open a terminal on a remote computer (the robot's Raspberry Pi) from your laptop over a network connection. When you SSH in, commands you type run on the robot.
Workspace
In ROS 2, a workspace is a folder containing all your packages and built code. SwayForm's workspace is at ~/ros2_ws. You must source it (source install/setup.bash) before running any ROS 2 commands.
Launch file
A ROS 2 script that starts multiple nodes at once. SwayForm uses a launch file on boot to start the motion node, camera node, and other background services automatically.
Motion lock
A mechanism that prevents two behavior scripts from commanding the same joint at the same time. When a lock is held by one behavior, others wait or are blocked. Prevents unsafe overlapping commands.
Behavior
A self-contained program or function that makes the robot do something — wave, greet, point, play a game. A behavior starts, runs its sequence of commands, and ends.
Safe limit
The maximum and minimum angle a joint can be safely commanded to. The motion node enforces these limits automatically, clamping any value that exceeds them to the boundary.
State machine
A way of organizing behavior into named states. The program is always in exactly one state, does the work for that state, then transitions to the next. Used in Demo 05 and Lab 10.
